How to read the numbers
  • Long task: the JS thread was busy for at least 50 ms without a break (same threshold as the web Long Tasks API). While that happens, taps, scroll callbacks, timers, network responses and JS-driven animations wait. Max JS block is the longest such freeze. Aim for 0 long tasks while scrolling.
  • Render ms/s: time React spent rendering components per second. Components / Files show self time, without children. Time of library components (View, Text, SvgXml…) is charged to the closest component of ours that renders them; Incl. library shows which ones.
  • Why: what changed for the component compared with its previous render — props: name, state, store (useSelector), context: Provider. parent rendered (props equal) means nothing it receives changed: it re-rendered only because its parent did and it is not memoized.
  • Compiler ✓ memo: React Compiler memoized the component; at runtime the probe saw useMemoCache on it. ✗ error/class/skipped: not memoized, and the reason comes from the compiler itself. Many renders with no prop changes and ✗ is the first thing to fix.
  • JS FPS / UI FPS: frames the JS / main thread delivered. On Android the UI value is the number of frames actually drawn (0 when idle is normal).
  • Hermes GC: garbage-collector CPU time and heap of the JS engine. ART GC (Android): Java/Kotlin garbage collector. A rising heap that never drops means a leak.
  • The probe build uses React's profiling renderer, so absolute numbers are a little higher than in the store build. Compare probe build vs probe build (before/after).
