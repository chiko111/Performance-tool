How to read the numbers
  • Long task: the JS thread was busy for at least 50 ms without a break (same threshold as the web Long Tasks API). While that happens, taps, scroll callbacks, timers, network responses and JS-driven animations wait. Max JS block is the longest such freeze. Aim for 0 long tasks while scrolling. Timers run on the display's frames and an idle screen drops to 10-24 Hz, so one frame of delay is not counted.
  • Render ms/s: time React spent rendering components per second. Components / Files show self time, without children. Time of library components (View, Text, SvgXml…) is charged to the closest component of ours that renders them; Incl. library shows which ones.
  • Why: what changed for the component compared with its previous render — props: name, state, store (useSelector), context: Provider. parent rendered (props equal) means nothing it receives changed: it re-rendered only because its parent did and it is not memoized.
  • Compiler ✓ memo: React Compiler memoized the component; at runtime the probe saw useMemoCache on it. ✗ error/class/skipped: not memoized, and the reason comes from the compiler itself. Many renders with no prop changes and ✗ is the first thing to fix.
  • JS FPS / UI FPS: frames the JS / main thread delivered. On Android the UI value is the number of frames actually drawn (0 when idle is normal).
  • WebSocket: messages the app received per socket and, for STOMP, per destination (topic); ids in the URL and topic are folded. Renders after are components rendered in the commit right after a message (within 100 ms), split between the topics that arrived before it: a topic with many renders per second is one that keeps the screen re-rendering. The line above the table shows how often each socket opened and closed (reconnects) and with which close codes.
  • Hermes GC: garbage-collector CPU time and heap of the JS engine. ART GC (Android): Java/Kotlin garbage collector. A rising heap that never drops means a leak.
  • The probe build uses React's profiling renderer, so absolute numbers are a little higher than in the store build. Compare probe build vs probe build (before/after).
  • Web (perf web): Frames is the page's frame rate. CPU by thread, Layout / Style ms/s, V8 GC, DOM nodes and Listeners come from Chrome or Edge (desktop, or Android Chrome over USB); Safari and Firefox show what the page itself measures. Forced synchronous layout: code read offsetHeight, getBoundingClientRect… right after changing the page, so the browser had to lay out inside the script — the row names the file and line. Slow frames: Chrome's long animation frames with the scripts that made them late. INP: time from an input to the next paint, split into waiting, handlers and paint. CLS: how much content jumped, with the elements that moved.
